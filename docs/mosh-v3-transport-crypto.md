# Mosh v3 transport crypto experiment

Status: experimental design for `experiment/mosh-v3-crypto`. This is not a claim of production readiness and does not change the default v2 wire protocol.

## Objective

Preserve the parts of Mosh that are unusually good: SSH bootstrap, roaming across IP/port changes, SSP state synchronization, predictive local echo, and tolerance of loss/reordering. Improve the cryptographic lifecycle for sessions that can remain alive for days or months.

The main problem to solve is not that AES-128-OCB is weak. Mosh v2 generates one 128-bit session key, sends it over SSH, and uses that same key in both directions for the lifetime of the UDP session. A v3 design should reduce the amount of traffic and elapsed time exposed by any one in-memory traffic key without turning Mosh into a general-purpose TLS/QUIC replacement.

## Prior art

`zmosh` is useful evidence that a Mosh-like roaming UDP transport can be kept simple with a modern AEAD. It uses XChaCha20-Poly1305, a 256-bit shared key, an authenticated nonce/sequence prefix, and updates the peer address only after successful authentication. It still has a single long-lived shared session key.

`moshpit` explores a much broader cryptographic surface: negotiated KEX, multiple AEADs, HMACs, and post-quantum options. That is useful prior art but is intentionally not the model here. V3 should have one small mandatory suite and no redundant MAC layered on top of AEAD.

## V3.0 cryptographic profile

Mandatory suite:

- SSH remains the authenticated bootstrap channel.
- 256-bit random bootstrap secret generated by `mosh-server`.
- HKDF-SHA-256 for all key derivation.
- Separate client-to-server and server-to-client traffic-secret chains.
- ChaCha20-Poly1305 with a 256-bit key, 96-bit nonce, and 128-bit authentication tag.
- No separate HMAC.
- Deterministic nonces derived from a per-epoch IV and the existing Mosh packet sequence number.
- Explicit traffic-key epochs and authenticated acknowledgement of the peer epoch.
- Secure erasure of bootstrap and retired traffic secrets/keys.

ChaCha20-Poly1305 is chosen over AES-GCM-SIV for the first implementation because it is widely available through OpenSSL EVP, does not depend on AES hardware, and is straightforward to implement across future native clients. XChaCha20-Poly1305 would also be reasonable but is not exposed by ordinary OpenSSL EVP. AES-128-OCB remains the v2 compatibility path.

## Bootstrap

V2 remains unchanged:

```text
MOSH CONNECT <port> <22-char-base64-key>
```

The experimental v3 bootstrap is versioned explicitly:

```text
MOSH CONNECT 3 <port> <43-char-base64-bootstrap-secret>
```

The 43-character value is unpadded base64 encoding of 32 random bytes.

The wrapper transports this message inside SSH as it already does for v2. The client derives directional traffic secrets and removes the bootstrap secret from the environment/process state as soon as practical.

A v3-capable wrapper should support both negotiation policies:

- `prefer-v3`: use v3 when both ends support it, otherwise fall back to v2.
- `require-v3`: fail rather than fall back.

Any negotiation transcript that selects v3/v2 must remain inside the authenticated SSH bootstrap so an on-path UDP attacker cannot force a downgrade.

## Initial key schedule

Let `bootstrap` be the 32-byte random value delivered through SSH.

```text
master = HKDF-Extract(
    salt = "mosh-v3 bootstrap",
    IKM  = bootstrap
)

c2s_secret[0] = HKDF-Expand(master, "mosh-v3 c2s traffic", 32)
s2c_secret[0] = HKDF-Expand(master, "mosh-v3 s2c traffic", 32)
```

For each direction and epoch:

```text
key[n] = HKDF-Expand(secret[n], "mosh-v3 key", 32)
iv[n]  = HKDF-Expand(secret[n], "mosh-v3 iv", 12)

secret[n+1] = HKDF-Expand(secret[n], "mosh-v3 traffic update", 32)
```

The bootstrap value and `master` are erased after the two epoch-zero traffic secrets are derived. The two directions never use the same traffic secret or AEAD key.

This hash ratchet gives forward protection for retired epochs if old secrets are actually erased: compromise of a later traffic secret does not reveal an earlier one. It does **not** provide post-compromise healing; an attacker who obtains the current traffic secret can derive later hash-ratchet epochs. An authenticated ephemeral X25519 refresh can be considered separately after v3.0 is mechanically sound.

## Datagram framing

V3 does not bind cryptography to an IP address or UDP port because authenticated roaming is a core Mosh property.

The cleartext authenticated header is fixed-width:

```text
0               1               2               6              10              18
+---------------+---------------+---------------+---------------+---------------+
| version = 3   | flags = 0     | send_epoch    | ack_epoch     | packet_seq    |
|    1 byte     |    1 byte     |    4 bytes    |    4 bytes    |    8 bytes     |
+---------------+---------------+---------------+---------------+---------------+
|                    ciphertext ...                             | tag (16 bytes) |
+---------------------------------------------------------------+----------------+
```

All multi-byte integers are network byte order. The full 18-byte header is AEAD associated data.

The encrypted plaintext remains the current Mosh packet body, including its transport timestamps and SSP payload. `packet_seq` is the same Mosh packet sequence used for ordering/freshness; moving it into the authenticated header avoids duplicating a second sequencing system.

Nonce construction for epoch `n`:

```text
nonce = iv[n]
nonce[4..12] ^= uint64_be(packet_seq)
```

Each directional key therefore has a deterministic, non-repeating nonce as long as packet sequence numbers do not repeat within an epoch. Key derivation also separates the two directions, so reflection across directions cannot authenticate.

## Key-update protocol

A naive time-based ratchet is unsafe for a roaming UDP protocol: one side can remain disconnected for hours while the other advances through multiple epochs. V3 therefore constrains an endpoint to be at most one unacknowledged outbound epoch ahead.

Each authenticated packet carries:

- `send_epoch`: the epoch used to encrypt this packet.
- `ack_epoch`: the highest peer epoch from which this endpoint has successfully authenticated a packet.

Rules:

1. A sender may move from epoch `n` to `n+1` when the rekey policy fires **only if epoch `n` is acknowledged by the peer**. Epoch zero is initially considered acknowledged for the purpose of allowing the first update.
2. After moving to `n+1`, the sender must remain there until it receives an authenticated peer packet acknowledging `n+1`.
3. A receiver accepts its current peer epoch, the immediately previous epoch during a bounded reorder grace period, or `current+1`.
4. A packet claiming `current+1` advances the receive epoch only after successful AEAD authentication with the derived candidate key.
5. Epoch jumps greater than one are rejected before any unbounded key derivation work. This prevents a spoofed datagram from turning a clear epoch field into a CPU amplifier.
6. Acknowledgements are monotonic. An old reordered packet cannot move the acknowledged epoch backwards.

This arrangement lets a session survive arbitrarily long network outages without either side racing its key schedule away from the other, while still permitting periodic key retirement during an active session.

Initial experimental rekey policy:

- after 60 minutes of active use, or
- after 2^20 packets sent in the current epoch,
- whichever occurs first,
- subject to the acknowledgement rule above.

These thresholds are policy, not cryptographic limits, and should be tunable/tested before production use.

## Reordering and replay

V3 must not blindly copy a strict `seq > highest_seen` filter. Mosh's transport and state synchronization tolerate packet reordering, and dropping every authenticated lower sequence number can unnecessarily turn reordering into loss.

The AEAD layer authenticates `packet_seq`; the existing Mosh transport remains responsible for deciding whether an authenticated packet is useful, duplicate, stale, or out of order. V3 can later add a bounded replay bitmap if profiling demonstrates value, but it must preserve the transport's existing reordering semantics.

## Roaming

A received source address becomes the peer's current address only after:

1. the v3 header passes structural checks,
2. epoch processing is bounded and valid,
3. AEAD authentication succeeds, and
4. the existing Mosh packet-freshness rules accept the packet as appropriate for association/roaming.

No IP address, UDP port, or address family is included in AEAD associated data.

## Secret handling

V3 should retain Mosh's existing core-dump suppression and add explicit secret erasure:

- erase the SSH-delivered bootstrap secret after derivation;
- erase `master` after directional secrets are created;
- erase a sender's previous traffic secret immediately after ratcheting;
- receivers retain only the material necessary for the bounded previous-epoch reorder grace period, then erase it;
- destructors erase all traffic secrets, AEAD keys, and IVs;
- avoid copying secret-bearing objects; use move-only/explicit ownership where practical.

Telemetry and moshwatch exports must never expose bootstrap secrets, traffic secrets, AEAD keys, IVs, plaintext, or packet captures.

## Compatibility boundary

V3 is a new wire protocol. It is not possible to silently substitute it for v2 while remaining compatible with an unmodified peer. The experiment must therefore leave the v2 `AES-128-OCB` path intact and make v3 an explicit capability selected during SSH bootstrap.

The first implementation should be OpenSSL-backed and compile only when the required EVP ChaCha20-Poly1305 and HKDF support are available. Other crypto backends can follow after the wire format and tests stabilize.

## Validation gates before any production claim

At minimum:

- deterministic HKDF test vectors;
- ChaCha20-Poly1305 known-answer and tamper tests;
- direction-separation tests;
- nonce uniqueness tests across packets and epochs;
- epoch update/acknowledgement state-machine tests;
- delayed and reordered old-epoch packet tests;
- long-disconnect then reconnect tests;
- source-address roaming only after authentication;
- downgrade-policy tests for `prefer-v3` and `require-v3`;
- fuzzing of header/epoch/decrypt parsing;
- cross-endian framing tests;
- explicit zeroization review;
- external cryptographic/security review before calling v3 production-ready.

## Deliberately deferred

V3.0 does not add algorithm agility, post-quantum KEMs, a second MAC, a new identity system, or a QUIC-style transport. It also does not initially attempt post-compromise healing.

A later extension may add an encrypted, authenticated X25519 key refresh. That should only be attempted after the simpler directional hash-ratchet protocol is proven under Mosh's loss, reordering, suspension, and roaming behavior.
